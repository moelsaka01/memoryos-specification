# MO-1309 release disclosures

Written in Phase 4D from recorded outcomes only. Candidate: `74be815b67a3e4e295bc2da0ff404ce379128d7f` (product bytes identical to B2 `9991a105`; later commits change tests, tooling and evidence only). Host: Windows 11 x64 (10.0.26200), Dell i7-1165G7, 15.7 GB, NTFS, Node.js v24.21.0, Microsoft Edge 155.0.4283.45. Windows Defender real-time monitoring was on (exclusions not visible without administrator rights); the host was shared with the operator's browser and chat applications, with total CPU samples of about 20–57 % before runs; Smart App Control was enforcing and untouched.

## What MO-1309 is, and is not

A downstream, read-only, static presentation of one verified MO-1308 history export, generated as one self-contained HTML file. It is an integrity view as of generation (Q-STORE-INTEGRITY below). It is not hosting, not a store, and not evidence of authenticity, completeness, currency or approval.

## Qualifications

- **Q-STORE-INTEGRITY.** Verification is integrity only: a fully self-consistent forged chain verifies; tail truncation and rollback are detectable only through an externally recorded `headDigest`, which the page shows in full with anchoring guidance. The MO-1308 store claim is unchanged (local single-user v1, native Windows 11 x64; H40 re-review recorded in Freeze section 10). The history is not encrypted, so a hosted snapshot discloses entry metadata (identifiers, subjects, digests, tombstone reasons, authority references) to anyone who can read it; access control is the operator's, not provided or claimed by MemoryOS. Purged records keep digest, member names, lengths, digests and subjects, and exports taken before a tombstone retain the bytes.
- **Q-SCALE.** The certified scale is 10,000 entries. Worst of five runs on the reference host (W1, `evidence/mo1309/phase2d-windows/`; budget in brackets): read 7.3 s (30 s), verify-only 7.8 s (30 s), view-model build 8.5 s (30 s), assemble 1.2 s (5 s), publish 0.2 s (5 s), generation wall 25.9 s (60 s), generator RSS 467 MB (1,100 MB), snapshot 8.9 MB (11 MB), load event 440 ms (1,600 ms), filter/sort/next page 17/10/29 ms (200 ms), page heap 14.3 MB (100 MB), 1,108 DOM nodes (3,000). The campaign case 4A-E4 passed within the same budgets.
- **Q-PERF-100K.** 100,000 entries are characterized only, with no pass, fail or support claim. One run on the reference host: read 227 s, verify-only 53 s, view-model build 67.5 s, assemble 11.2 s, generation wall 363 s (about 6 minutes), generator RSS 2,127 MB, snapshot 88.8 MB, load event 2.3 s, filter/sort/next page 52/69/69 ms, page heap 98.9 MB. Exporting 100,000 entries with the MO-1308 CLI took about 16 minutes (MO-1308 Q11) and remains a separate maintenance item (DB32).
- **Q-HOST.** The performance numbers come from a non-idle laptop (see above); the budgets were derived from a cloud host, and the Windows run was within them. The browser was Edge 155.0.4283.45, not Chrome; the campaigns do not record the browser build, this document and the handoff do.
- **Q-TOOLING.** The certifying campaigns 4A, 4B and 4C ran with the tooling of commits `68eed767` and `f8bcf30f`. Test and tooling fixes made afterwards (the `npm` runner on Windows, the differential gate on Windows and Node 24, one unit test) are in the candidate `74be815b`; none touches a product byte or an assertion about product behaviour. The mo1309-tools suite was therefore run again at the candidate as its own row (run 2, 32/32).
- **Q-GATE-NODE.** The Node-driven differential gate (generation 2) is `PASS_QUALIFIED_CLOUD_SUBSET`: the verdict name is fixed by the tool, and here "qualified" means `tools/verify_workspace.py` exits 2 on both BF and the candidate when run directly in a fresh worktree, so rule 1 is established by the CTest test `cca.workspace.verify`, which passes on both (Q-CTEST). 99 units at BF, 104 at the candidate (5 new MO-1309 units pass), 0 regressions, 0 new failures, 15 shared failures identical at BF. Their classification, including the five the cloud left undetermined, is in [the classification](mo1309-differential-classification.md).
- **Q-GATE-LONG-UNITS.** `mo1308_phase3b_test.mjs` and `mo1308_phase3d_test.mjs` were killed by the gate's 900 s per-unit limit on BF and on the candidate, so the gate compared no tests for them. A supplementary run without the limit (preserved as INTERRUPTION in `evidence/mo1309/differential-node-supplement/`) showed `mo1308_phase3b` identical on both sides (17 of 21 pass, the same four failing tests, A01, B02, N07, S03) and `mo1308_phase3d` hanging on BF with no output for 30 minutes and an idle child `git.exe`; it was stopped by hand and not run on the candidate. The owner accepted both as unchanged: they are MO-1308 units, behave identically at BF and the candidate, and MO-1309 adds no code they exercise. They were not retried.
- **Q-CTEST.** The CTest differential (preset `default`, MSVC 19.44, BF versus the candidate, one run each) is `PASS`: 317 registered, 2 excluded (`cca_core_tests_NOT_BUILT`, the A3.1 MSVC C2607 waiver; and `memoryos.sdk.cpp.regression.example`, a native binary Smart App Control blocked in one probe round, A3.3), 315 executed per side: 192 passed on both, 123 failed on both with identical results, no new failure, no candidate-only test, `cca.workspace.verify` passes on both. `cca_core_tests` does not compile with this MSVC and was not run; the C and C++ sources are identical between BF and the candidate. Native C++ verification belongs on a host without Smart App Control.
- **Q-SHARED-FAILURES.** The 123 shared CTest failures are the same set and classes as in the MO-1308 A3.2 record (112 `*AllocationFailureTest` aborts, the MCP integrity and artifact failures, the hard-coded workspace path, the stale 1.2.1 pin, the missing Standard publication, and `memoryos.standard.runtime.reference` Not Run because of the waiver); each has a reason in `evidence/mo1309/differential-ctest/receipt.json`.
