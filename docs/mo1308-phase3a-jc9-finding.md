# MO-1308 Phase 3A rehearsal r6: finding at 3A-JC9 (PRODUCT DEFECT, preserved, not fixed)

Classification: **PRODUCT_DEFECT_WRONG_ERROR_CODE_AT_THE_ENTRY_CEILING** (found by the non-certifying rehearsal `phase3a-rehearsal-r6`, candidate `f4211c8c`; the rehearsal otherwise passed 106 of 108 cases: main1 16 min, main2 26 min, ceiling segment 28 min before the stop; 3A-JC10 not run). The harness is not at fault; no production file, case or expectation was changed.

Observed: with a ledger holding exactly 100,000 entries (the last one appended by the real production store, 3A-JC5), a further valid `append` of an `INVESTIGATION_CHECKPOINT` (the same file appends cleanly into a fresh ledger) is refused with exit 2 `MO1308_RECORD_INVALID` at stage `ADMISSION`. Nothing is changed (the refusal is clean). Expected by the protocol (3A-JC9) and the Freeze (section 14.2 limits, error table: `RESOURCE_LIMIT` = "a section 14.2 limit exceeded"): `MO1308_RESOURCE_LIMIT`.

Cause (read from the code, reproduced with a scratch script that only calls the production store on the preserved ledger): `appendHistoryEntry` (`repositories/cca-studio/web/js/memoryos-history-ledger.js:262-270`) builds the would-be entry with `index = state.entries.length` (100000) and runs `validateEntry(parsed, { code: "RECORD_INVALID", stage: "ADMISSION" })`; the shape check `isIndex` (`memoryos-history-contract.js:230`) allows `index <= maximumIndex` (99,999), so it fails with RECORD_INVALID before the `RESOURCE_LIMIT` test in `sealEntry` (`memoryos-history-ledger.js:236`, `state.entries.length >= entriesPerLedger`) can run. Unchanged by A10 (the A10 paths are `bin/memoryos.js` and `src/history-store.js` only); present in b0bf2d56 and the Phase 2 code.

Reproduction: `C:\v6a\.p3a-work\rehearsal-r6\ceiling` (ledger of 100,000 entries, `checkpoint.json`, kept for diagnosis) then `node repositories/memoryos-cli/bin/memoryos.js history append --ledger <ledger> --kind INVESTIGATION_CHECKPOINT --record <checkpoint.json> --json` gives `MO1308_RECORD_INVALID`. Smaller ledgers append the same file normally (3A-JC9 at 3,000 entries appends).

Decision needed from the owner (not taken here): (a) correct the product (check the entry limit first, a production change needing its own binding, A3.2 differential and candidate move), or (b) amend the Freeze/protocol so the 100,001st append may be `RECORD_INVALID` or `RESOURCE_LIMIT` (a weakening of 3A-JC9, which this work will not do without an amendment). Until then a certifying 3A run would fail 3A-JC9 and burn the generation.
