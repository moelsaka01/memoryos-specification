# Startup resolution post-repair validation

Prepared adapters only. Do not execute or freeze them before the one diagnostic
capture, trace-driven repair and final static review. No accepted candidate is
implied. Preserve all prior failed generations, including headless cleanup.

Use the provisioned SHA-256-pinned Node 24.21.0 win-x64 runtime from the isolated
correction worktree. The commands below have fixed source/evidence paths and no
case, launch, output or deadline overrides.

1. After the single diagnostic execution identifies a concrete mechanical
   defect, root applies the smallest repair and refreshes package metadata.
   Finalize the new report `docs/mo1307-startup-resolution.md`, preserve the old
   sealed `docs/mo1307-headless-cleanup-correction.md`, and bind both plus this
   generation's user request. Root writes `repair-binding.json` under the new
   evidence root with kind `MO1307StartupResolutionRepairBinding`, result
   `READY_FOR_ONE_POST_REPAIR_SMOKE`, `candidate:null`, `repairApplied:true`, the
   exact 89 current `source` records, `diagnostic` receipt record, optional
   `diagnosis` file record, and ordered `governance` records (old correction
   spec, new request, new report). An implementation conflict is a STOP.
2. Review the exact repaired `Confirm-ConsoleQuiescence` extraction, substituted
   native-method signatures/returns, matrix cases and receipt expectations.
   Current doubles are preparation, not proof that an unknown repair needs no
   adapter changes. Root runs `minimum-wire-smoke.mjs` exactly once, then only
   on PASS runs `security.mjs` once. The smoke requires the bound one-invocation
   captured diagnosis and repair. It uses the headless-cleanup failure only for
   runtime provenance, never as the repaired source authority. Any failure is a
   STOP; no additional diagnosis, smoke or fallback invocation is allowed.
3. Run `node repositories/cca-conformance/tools/mo1307-startup-resolution/validation-bindings.mjs prepare`
   once. This inventories exact source/tool/test/fixture/runtime bytes and
   predeclares short-alias applicability. It requires both
   `evidence/mo1307/startup-resolution/minimum-wire-smoke/receipt.json` and
   `evidence/mo1307/startup-resolution/security/receipt.json` to report PASS,
   unchanged sources and these exact 89 current members. The manifest has
   `candidate:null`; preparation executes no product, helper or test.
4. Run `node repositories/cca-conformance/tools/mo1307-startup-resolution/regressions.mjs`
   once. Package consistency must pass with 89 members, 53 contract members and
   zero dependencies. The existing test files then run in order: package8,
   launch13, runtime36, protocol/publication24, timer1, native-foundation25,
   totaling 107. Failure stops before the next command. Each original test file
   retains its existing internal case scheduler.
5. Only after PASS, run `node repositories/cca-conformance/tools/mo1307-startup-resolution/native-filesystem.mjs`
   once. Its 33 mandatory cases contain 36 helper invocations. A predeclared
   existing distinct short-path alias adds one case and two invocations. Alias
   absence is not applicable, never PASS. Fixture setup failures stop the suite.
6. Only after PASS, run `node repositories/cca-conformance/tools/mo1307-startup-resolution/toctou.mjs`
   once. Its two preserved mutation-window controls each execute one reversible
   copy of the current helper. Only the copy's script path differs from the
   fixed production launch. The exact original bytes are recovered by removing
   instrumentation. Releasing a sharing restriction is an explicit engineering
   fixture device; no historical helper or Phase 3C campaign is executed.
7. Only after all implementation validation passes may the root task commit a
   new candidate and bind its exact 89 members to the validated source manifest.
   That Git identity must be recorded separately from the source hash. Fresh
   Phase 3A packaging, offline install, complete A-O inventory and once-only
   certification belong to a new worktree/generation. Phase 3B/3C are not run.

Every required command/native exchange and closure rechecks prerequisite
receipt bindings, all source/test/tool/fixture bytes, runtime executables, fixed
launch and alias applicability. Do not change bound tools after preparation.
